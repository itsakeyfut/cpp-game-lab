# ADR-0002: ゲームエンジン・エディタを使わず raylib を使う

- 状態: 承認
- 日付: 2026-10-06

## 背景
- C++ で、Unreal Engine を使わずにゲームモデルを定義してゲームを作りたい。
- ゲームエディタは使わず、すべてコードで構築したい。
- 学んだ設計を、後に Unreal Engine で手書きする開発に活かしたい。
- 「実際に遊べるゲーム」と「3D ゲームシミュレーション」のどちらを作るかも決める必要があった。

## 決定
- 実際に遊べるゲームとシミュレーションの両方を兼ねる。ゲームのルールは描画ライブラリに依存しないシミュレーションコアとして書き、その外側に raylib による薄い描画・入力層を載せる（構造は [ADR-0003](0003-functional-core-imperative-shell.md)）。
- 描画・入力ライブラリは raylib。Godot・SDL3 は採用しない。
- ゲームエディタは使わない。

## 検討した選択肢
| 観点 | **raylib** | Godot（GDExtension / C++） | SDL3 |
|------|-----------|---------------------------|------|
| エディタなしでの開発 | 元々エディタがないため自然 | 可能だが、エディタ前提の設計（シーン `.tscn`・インスペクタ）と戦うことになる | 自然 |
| 継承 vs 合成 | 関数群のみ。構造を自分で決められる | `Node` を継承してシーンツリーに載せるのが基本で、合成方針と衝突する | 構造を自分で決められる |
| FP / 純粋関数 | ゲームループを自分で書くため、純粋な `Step` 関数を中心に置ける | エンジンのライフサイクル（`_process` 等）に従う必要がある | 同左（raylib） |
| 3D 描画の手間 | カメラ・メッシュ・ライティングが少ないコードで扱える | エンジンが提供 | SDL_GPU で自前実装が必要。学習の焦点がグラフィックス API に逸れる |
| 立ち上げ・構成の学習 | CMake・ディレクトリ・モジュール分割を全て自分で決める | エンジンが構成を決めるので学べない | 自分で決める |
| UE への転用 | 「エンジンが何を肩代わりしているか」を自作で理解できる | godot-cpp のバインディング知識は UE で使えない | raylib と同じ |

## 結果
- ゲームループ・Tick・World / Component の仕組みを自作することで、UE の `UWorld` / `AActor` / `UActorComponent` の役割を理解しやすくなる。
- ロジックをエンジン非依存の C++ に分ける設計は、UE でも素の C++ 構造体やモジュールでそのまま使える。
- UE 固有の仕組み（UObject の GC、リフレクションマクロ、Blueprint、UBT）はこのプロジェクトでは学べない。UE に移ってから学ぶ。
