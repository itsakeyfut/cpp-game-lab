# ADR-0001: 決定を ADR として記録する

- 状態: 承認
- 日付: 2026-10-07

## 背景
このプロジェクトの学習目標の 1 つは、立ち上げから成長までの変遷を後から観察することにある（[project-overview.md](../project-overview.md)）。コードとコミット履歴だけでは「なぜそうしたか」「何と比べたか」が残らない。

## 決定
- 設計・構成に関わる決定は ADR（Architecture Decision Record）として `docs/adr/`（全体）と `games/<題材>/docs/adr/`（題材固有）に記録する。
- 「今どうなっているか」はガイド文書（`docs/*.md`、設計書）に書き、「なぜそう決めたか」は ADR に書く。
- 書いた ADR は書き換えない。方針を変えるときは新しい ADR を追加し、古い ADR を「廃止」にする。

## 検討した選択肢
| 選択肢 | 長所 | 短所 |
|--------|------|------|
| **ADR（1 決定 1 ファイル）** | 業界で広く使われる形式。決定ごとに背景と比較を残せる。廃止・置き換えの履歴が追える | ファイル数が増える |
| 1 つの決定一覧ファイル | 一覧性が高い | 理由や比較が長くなると読みにくい。変更履歴が混ざる |
| コミットメッセージ・PR のみ | 追加の文書が不要 | 後から探しにくい。設計全体を見渡せない |

## 結果
- 方針の変更も「廃止された ADR」として残るため、考えが変わった経緯を追える（例: [ADR-0005](0005-monorepo-engine-and-games.md)）。
- ガイド文書は常に最新の状態だけを書けばよくなる。
