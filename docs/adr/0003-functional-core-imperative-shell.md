# ADR-0003: Functional Core, Imperative Shell と FP 中心の設計

- 状態: 承認
- 日付: 2026-10-07

## 背景
- 継承を抑えて合成で構成したい。
- 純粋関数・イベント・メッセージングで設計し、FP スタイルをなるべく多く取り入れたい。
- 実際に遊べるゲームにする以上、入力・描画・ファイル読み込みといった副作用は避けられない。

## 決定
**Functional Core, Imperative Shell**（純粋な中核と、副作用を持つ薄い外殻）で構成する。
```
app（副作用: 入力・描画）
  入力 → InputFrame
  sim::Step(config, state, input, dt) → { state, events }   ← 純粋関数
  events で演出、state を描画
```
- ゲームのルール（sim）はすべて純粋関数。同じ入力なら必ず同じ結果を返す。乱数生成器も状態の一部として値で受け渡す。
- `Step` は固定タイムステップで呼ぶ。描画は可変フレームレート。
- `Step` の内部は小さな純粋関数をつないだパイプラインにする。段階同士は中間データとイベント（値）で受け渡し、互いを直接呼ばない。
- 「何が起きたか」はイベント（`std::variant` の値）として返す。副作用を持つコールバックは使わない。
- データは小さな部品 struct の集約で表し、「決まった選択肢のどれか 1 つ」は `std::variant` + `std::visit` で表す。仮想関数による多態は使わない。
- 状態は値で受けて新しい値を返す。呼び出し側は `std::move` で渡し、コピーを発生させない。

## 検討した選択肢
| 選択肢 | 長所 | 短所 |
|--------|------|------|
| **Functional Core, Imperative Shell** | ルールを描画なしでテストできる。決定論的でリプレイ・デバッグが容易。FP の方針を最も素直に表現できる | 状態全体を受け渡すため、書き方に慣れが必要 |
| オブジェクト指向（各オブジェクトが自分の `Update()` を持つ） | UE・Unity と同じ形で馴染みがある | 副作用が全体に散らばり、テストと決定論の確保が難しい。継承に寄りやすい |
| ECS（システムがレジストリを書き換える） | 大量のエンティティに強い | 可変なレジストリが中心で、純粋関数にしにくい |

## 結果
- UE との対応: `Step` ↔ `UWorld::Tick`、イベント ↔ Delegate / Gameplay Event、`InputFrame` ↔ Enhanced Input の Input Action の値（[ue-mapping.md](../ue-mapping.md)）。
- UE の Actor は自分自身を更新するが、本プロジェクトは 1 つの純粋関数が全体を更新する。この違いを比較できること自体が学習になる。
- 性能面の懸念（状態のコピー）は、ムーブでの受け渡しと計測で確認する（[arena ADR-0001](../../games/arena-survival/docs/adr/0001-entity-representation-value-arrays.md)）。
