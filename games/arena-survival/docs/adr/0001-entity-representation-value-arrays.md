# ADR-0001: エンティティは部品の集約 + 値の配列で表す（ECS を使わない）

- 状態: 承認
- 日付: 2026-10-07

## 背景
- プレイヤー・敵・弾・アイテムを、合成（[ADR-0003](../../../../docs/adr/0003-functional-core-imperative-shell.md)）でどう表すかを決める必要があった。
- 弾は大量に発射され、アイテムは 1,000 個スポーンする可能性がある。大量にスポーンするものは ECS の方が良いのではという懸念があった。

## 決定
- 種類ごとに、共通の小さな部品 struct（`Kinematics` / `Collider` / `Health` / `Weapon` / `Lifetime` など）を集約した struct で表す。
  ```cpp
  struct Enemy { EnemyId id; Kinematics kinematics; Collider collider; Health health; Behavior behavior; int scoreValue; };
  ```
- 関数は部品単位の純粋関数として書く（`ApplyDamage(Health, int) -> Health`）。
- 大量にスポーンする弾・アイテムも含め、すべて種類ごとの `std::vector` に値で保持する。状態はムーブで受け渡す。
- 性能目標を決め、ベンチマークを CI で計測する。初期値: **弾 10,000 + 敵 500 + アイテム 1,000 で `Step` 1 回が 2ms 以内**（release）。
- 目標を割った場合は、計測結果をもとに SoA（部品ごとの配列）や ECS への変更を検討する。
- 弾 × 敵の当たり判定は、空間分割（一様グリッド）で対処する（M7）。

## 検討した選択肢
| 選択肢 | 長所 | 短所 |
|--------|------|------|
| **A. 種類ごとの配列 + 部品の集約** | 型で構成が決まり読みやすくテストしやすい。値型なので純粋関数と相性が最も良い。UE の Actor + Component の構成に近い | 実行時にコンポーネントを付け外しできない |
| B. ECS（EnTT など） | 業界で人気。大量のエンティティに強い。実行時に部品を付け外しできる | レジストリを書き換える設計で純粋関数にしにくい。この規模では過剰 |
| C. 汎用エンティティ + 任意の部品（`optional<Health>` など） | 柔軟 | `optional` の確認が至る所に出る。型で構成が保証されない |
| A と B の混在（プレイヤー・敵は A、弾・アイテムは ECS） | 大量スポーンに ECS を使える | 1 つのゲームに 2 つの方式が混ざり、状態の受け渡し・テスト・純粋関数化の書き方が 2 通りになる |

## 計測（2026-10-07）
方式 A の格納を、純粋関数スタイル（`World Step(World, dt)`）で計測した。
- 条件: 毎ステップ弾を 200 発生成、寿命 2 秒（定常状態で弾 24,000 発 + アイテム 1,000 個）、移動・寿命切れの削除・アイテム更新。clang++ -O2。

| 状態の渡し方 | 1 ステップあたり | 60Hz の予算 16,667µs に対する割合 |
|--------------|------------------|-----------------------------------|
| ムーブで渡す | 約 48µs | 約 0.3% |
| 毎回まるごとコピー | 約 417µs | 約 2.5% |

分かったこと:
- ECS の速さの源は「同じ種類の部品が配列に連続して並ぶこと」。同じ種類の弾だけを `std::vector` に並べる方式 A はその状態になっており、数が多いこと自体は ECS を選ぶ理由にならない。
- ECS が本当に効くのは「実行時に部品を付け外しする」「種類をまたいで処理する（『Health を持つもの全部』）」場合。
- 純粋関数でも、状態をムーブで渡せばコピーは発生しない。
- 実際に重くなるのは当たり判定の総当たり（数の掛け算）で、格納方式ではなく空間分割で解決する問題。

## 結果
- 「推測せず計測する」。ECS が必要になったら計測結果を添えてこの ADR を廃止し、新しい ADR を書く。その経緯自体が学習記録になる。
- ECS は題材シリーズ #6（コロニー / RTS）の学習テーマとして扱い、方式 A と比較する。
