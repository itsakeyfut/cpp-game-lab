# ADR-0003: マイルストーンとデータ駆動化の時期

- 状態: 承認（マイルストーンのタグは [ADR-0018](../../../../docs/adr/0018-no-tags-or-versions.md) により廃止）
- 日付: 2026-10-07

## 背景
- 学習目標は、プロジェクトの立ち上げから成長までの変遷を観察すること。
- 最初から完成形の設計で作ると、「なぜその仕組みが必要になったか」が履歴に残らない。

## 決定
「動く最小のもの」から始め、作り直し（リファクタリング）も含めて成長させる。各マイルストーンでタグ `arena-survival/vX.Y.Z` を付ける。

| # | 内容 | 主に学ぶこと |
|---|------|-------------|
| M0 | 立ち上げ: CMake / プリセット / vcpkg / 品質ツール / CI / `engine::core` / raylib の空ウィンドウ / テスト 1 本 | プロジェクトの立ち上げ手順 |
| M1 | プレイヤーが動く | Functional Core の骨格 |
| M2 | 射撃と弾 | 値型の配列・ムーブでの受け渡し |
| M3 | 突撃型の敵・当たり判定・HP・撃破・スコア | イベント（メッセージング） |
| M4 | ウェーブ・タイトル / ゲームオーバー / リスタート | 状態遷移、決定論的な乱数 |
| M5 | データ駆動化（JSON → `GameConfig`） | Result による読み込みと検証 |
| M6 | 射撃型の敵・アイテム | 既存設計への機能追加のしやすさ |
| M7 | ベンチマーク・空間グリッド | 計測に基づく最適化 |

**データ駆動化は M5 まで行わない。** M4 まではゲームバランスの値をコード（`DefaultConfig()`）に直接書き、M5 で JSON 読み込みに移行する。

## 検討した選択肢
| 選択肢 | 長所 | 短所 |
|--------|------|------|
| **M5 でデータ駆動化** | 「値が増えてコードに書くのがつらくなった」時点での移行が履歴に残る。`Step` が最初から `GameConfig` を受け取る形にしておけば、移行は設定の出所の差し替えだけで済む | M4 までは値の調整にビルドが必要 |
| 最初からデータ駆動 | 値の調整が最初から容易 | 必要性が生まれる前に仕組みを作ることになり、変遷が残らない |

## 結果
- 設計書と実装がずれた場合は設計書を更新し、重要な変更は新しい ADR として記録する。
